# 16 — 新增能力多交付接入规范

## 16.1 文档目标

本文档用于沉淀当前已经在 `face_detect`、`liveness_action`、`idcard_detect` 与 `doc_classify` 上验证通过的多交付模板接入方式，指导后续新增能力时，按统一模式接入以下三类交付形态：

1. Linux SO SDK
2. JNI 交付
3. Windows DLL 交付

本文档聚焦**代码接入规范**，默认能力插件本身已经具备标准 `C ABI` 导出接口，并已纳入 `src/plugins/` 构建。

## 16.2 已验证模板范围

当前已完成并验证的能力：

- `face_detect`
- `liveness_action`
- `idcard_detect`
- `doc_classify`

当前已验证通过的交付层：

- Linux SO SDK
- Windows DLL
- JNI 模板结构与条件构建

其中 JNI 在当前环境下由于缺少 `JNI/JDK` 工具链，采取条件构建与自动跳过策略；但桥接代码、Java bridge、Java demo 与 CMake 组织方式已经完成模板化。

## 16.3 通用层与能力专属层划分

### 16.3.1 通用层

以下文件属于多能力复用层，新增能力时应优先复用，不应重复实现：

- `src/sdk/linux_so/sdk_loader.h`
- `src/sdk/linux_so/sdk_loader.cpp`
- `src/sdk/linux_so/capability_sdk.h`
- `src/sdk/linux_so/capability_sdk.cpp`
- `src/jni/jni_bridge_common.h`
- `src/jni/jni_bridge_common.cpp`
- `src/sdk/windows_dll/dll_exports.h`

职责划分如下：

- `SdkLoader`
  - 负责动态加载插件动态库
  - 负责解析标准插件符号
  - 负责执行 `init / infer / free_result / get_info`

- `CapabilitySdk`
  - 负责将媒体输入封装为 `AiPluginInput`
  - 负责向能力插件发送 `base64 + format + media_type + params_json`
  - 负责返回统一结构 `CapabilitySdkResult`

- `jni_bridge_common`
  - 负责 JNI 公共桥接版本等通用能力

- `dll_exports.h`
  - 负责统一 Windows DLL 导出宏

## 16.4 新增能力接入前提

新增能力进入多交付模板前，需要满足以下条件：

1. 插件代码已存在于 `src/plugins/<capability>/`
2. 插件已纳入 `src/plugins/CMakeLists.txt`
3. 插件导出以下标准符号：
   - `ai_plugin_init`
   - `ai_plugin_destroy`
   - `ai_plugin_infer`
   - `ai_plugin_free_result`
   - `ai_plugin_get_info`
4. 插件的 `ai_plugin_get_info(...).capability_id` 返回值稳定且正确
5. 插件输入模型已明确：
   - 图片型能力
   - 视频型能力
   - 帧序列型能力
   - 是否需要 `params_json`

## 16.5 Linux SO SDK 接入步骤

### 16.5.1 新增能力专属头文件

在 `src/sdk/linux_so/` 下新增：

- `<capability>_sdk.h`

推荐模式：

- `using XxxSdkResult = CapabilitySdkResult;`
- 能力类内部持有 `CapabilitySdk`
- 对外只暴露能力语义方法，不直接暴露底层 `AiMediaType`

例如：

- 图片能力：`infer_image_base64(...)`
- 视频能力：`infer_video_base64(...)`
- 帧序列能力：`infer_frame_sequence(...)`

### 16.5.2 新增能力专属实现

在 `src/sdk/linux_so/` 下新增：

- `<capability>_sdk.cpp`

实现约束：

1. 初始化直接复用 `CapabilitySdk::initialize(...)`
2. 对外能力函数内部调用 `CapabilitySdk::infer_media_base64(...)`
3. 根据能力类型传入正确的：
   - `media_type`
   - `media_format`
4. 若能力需要业务参数，可在能力封装层组装 `params_json`
5. 需要透传授权诊断能力，至少支持：
   - `last_error()`
   - `last_license_failure_reason()`
   - `last_license_failure_detail()`
6. 调用方读取授权失败信息时，优先使用稳定字段：
   - `last_license_failure_reason()`
   - `last_license_failure_detail()`
   而不是解析 `last_error()` 文本

### 16.5.3 新增 sample 与测试

新增：

- `<capability>_sdk_sample.cpp`
- `test_<capability>_sdk.cpp`

验证要点建议至少覆盖：

1. 初始化成功
2. `capability_id()` 返回值正确
3. 推理成功
4. 结果 JSON 中包含能力关键字段
5. 至少一个授权失败场景，并断言：
   - 兼容错误文本仍可读
   - `last_license_failure_reason()` 返回稳定原因
   - `last_license_failure_detail()` 返回稳定细节

### 16.5.4 新增测试

新增：

- `test_<capability>_sdk.cpp`

测试建议至少覆盖：

1. 初始化成功
2. 能力 ID 一致
3. 推理结果 `code == 0`
4. 结果 JSON 含关键能力字段

### 16.5.5 更新 CMake

更新 `src/sdk/linux_so/CMakeLists.txt`：

1. 新增 `ai_sdk_<capability>` 静态库
2. 新增 `<capability>_sample`
3. 新增 `test_<capability>_sdk`
4. 为测试补 `add_test(...)`
5. 测试参数需要传入：
   - 对应插件动态库路径
   - `model_dir`

## 16.6 JNI 接入步骤

### 16.6.1 新增 JNI C++ 桥接

在 `src/jni/` 下新增：

- `<capability>_jni.cpp`

实现规范：

1. 直接复用能力专属 SDK，而不是直接操作 `SdkLoader`
2. 提供以下最小接口：
   - `nativeVersion()`
   - `nativeCapabilityId(...)`
   - `nativeLastLicenseFailureReason(...)`
   - `nativeLastLicenseFailureDetail(...)`
   - `nativeInfer(...)`
3. 使用 `jstring -> std::string` 的统一转换逻辑
4. 返回值当前统一使用 `String`，承载：
   - 成功时返回结果 JSON
   - 失败时返回错误消息
5. 对需要自动化诊断的调用方，应优先提供稳定失败原因查询接口，而不是解析失败字符串

### 16.6.2 新增 Java bridge

新增：

- `<Capability>JniBridge.java`

Java bridge 规范：

1. 包名统一为 `ai.platform.sdk`
2. 提供 `loadLibrary(...)`
3. 对 native 方法提供简单 Java 包装方法
4. 类名与 native 符号一一对应
5. 需要补齐稳定授权失败原因包装方法：
   - `lastLicenseFailureReason(...)`
   - `lastLicenseFailureDetail(...)`

### 16.6.3 新增 Java demo

新增：

- `<Capability>JniDemo.java`

用途：

- 演示如何加载 JNI 动态库
- 演示如何调用 `capabilityId(...)`
- 演示如何执行一次最小推理

### 16.6.4 更新 CMake

更新 `src/jni/CMakeLists.txt`：

1. 在 `JNI_FOUND` 条件下新增 `ai_jni_<capability>`
2. 链接对应 `ai_sdk_<capability>`
3. 在 `Java_FOUND` 条件下，将新增 Java 文件加入 `AI_JNI_JAVA_SOURCES`

### 16.6.5 条件构建原则

JNI 层必须满足以下原则：

1. 找不到 `JNI` 头文件时，不报错，不阻塞主构建
2. 找不到 `Java Development` 工具链时，不生成 `jar`，但不阻塞主构建
3. 仅在环境满足时才产出：
   - `ai_jni_<capability>`
   - `ai-capability-sdk.jar`

在 `src/sdk/windows_dll/` 下新增：

- `<capability>_dll.cpp`

实现规范：

1. 直接复用能力专属 SDK
2. 维护最小全局状态：
   - SDK 对象
   - 输出 JSON 缓冲
   - 错误消息缓冲
   - capability_id 缓冲
   - license 失败原因缓冲
   - license 失败细节缓冲
3. 暴露以下最小接口：
   - `ai_<capability>_sdk_version()`
   - `ai_<capability>_initialize(...)`

## 16.8 能力类型与参数映射建议

| 能力类型 | 推荐 SDK 封装 | `AiMediaType` | `params_json` |

## 16.9 当前推荐新增能力接入顺序

按照当前模板成熟度，推荐新增能力接入顺序如下：

1. 先接 Linux SO SDK
2. 再接 Windows DLL
3. 最后接 JNI

原因：

- Linux SO SDK 最容易验证能力输入输出语义
- Windows DLL 复用 SDK 最直接，适合继续做交付模板收敛
- JNI 受外部环境影响更大，适合在已有 SDK 成熟后接入

## 16.11.1 License 失败诊断字段约定

当前模板已经统一了三类交付形态的授权失败诊断语义，新增能力接入时应保持以下约定不变：

### HTTP 状态接口

- `/api/v1/license/status` 需要输出：
  - `failure_reason`
  - `failure_detail`
  - `effective_now`
  - `in_grace_period`
  - `expired`

### HTTP 拒绝响应

- 当 HTTP 因授权失败返回 `403` 时：
  - 现有错误码与 `message` 保持兼容
  - 在 `data` 中附加：
    - `license_failure_reason`
    - `license_failure_detail`

### Linux SO SDK

- 兼容层：
  - `last_error()` 仍可直接给人阅读
- 稳定字段：
  - `last_license_failure_reason()`
  - `last_license_failure_detail()`

### Windows DLL

- 兼容层：
  - `error_message`
- 稳定字段：
  - `ai_<capability>_last_license_failure_reason()`
  - `ai_<capability>_last_license_failure_detail()`

### JNI / Java bridge

- 兼容层：
  - `nativeCapabilityId(...)` / `nativeInfer(...)` 失败时仍直接返回错误字符串
- 稳定字段：
  - `nativeLastLicenseFailureReason(...)`
  - `nativeLastLicenseFailureDetail(...)`
  - Java 包装层：
    - `lastLicenseFailureReason(...)`
    - `lastLicenseFailureDetail(...)`

### 原则

1. 错误码与原有 `message` 文本优先保持兼容
2. 调用方需要做自动化诊断时，优先读取稳定字段，不解析错误文本
3. 能力被拒绝时，稳定原因应区分：
   - `capability_denied`
   - `capability_not_in_license`

### 常见 `failure_reason` 与排查建议

以下 `failure_reason` 当前已经在主链路中落地，HTTP / SDK / DLL / JNI 应按统一语义理解：

| `failure_reason` | 含义 | 常见排查动作 |
|------|------|------|
| `license_file_open_failed` | license 文件无法打开 | 确认路径是否存在、服务账号是否有读取权限、部署环境是否正确挂载 license 文件 |
| `license_format_invalid` | license 文件格式不符合约定，例如缺少 payload/signature 分隔 | 重新生成 license 文件，避免手工编辑破坏文件结构 |
| `license_fields_missing` | license 缺少必要字段 | 对照当前 schema 重新生成 license，确认 `license_id`、指纹、能力列表、签名等关键字段齐全 |
| `fingerprint_mismatch` | 当前机器指纹与 license 绑定指纹不一致 | 重新获取目标机器指纹并签发 license，确认没有将测试机 license 部署到其他机器 |
| `signature_invalid` | license 签名校验失败 | 确认 license 未被篡改，检查生成与校验逻辑是否使用同一签名规则 |
| `not_yet_effective` | license 尚未到生效时间 | 检查 `effective_from`、系统时间与 `AI_PLATFORM_LICENSE_NOW` 覆盖值 |
| `expired` | license 已过期且不在宽限期内 | 检查 `expires_at`、`grace_period_hours`、系统时间与续签流程 |
| `license_invalid` | 已知校验失败，但未命中特定结构化原因 | 优先查看 `failure_detail`，并结合签名、时间窗口、文件内容做进一步排查 |
| `capability_denied` | capability 在 `denied_capabilities` 中被显式拒绝 | 确认该能力是否应被禁用，若需开通则从 `denied_capabilities` 中移除 |
| `capability_not_in_license` | capability 不在 `licensed_capabilities` 中 | 重新签发包含该 capability 的 license，确认能力 ID 与插件导出 capability ID 完全一致 |

补充说明：

1. `failure_detail` 优先承载底层原始失败细节，适合直接进入日志与排障页面
2. `failure_reason` 适合做程序分支判断、指标聚合和告警分类
3. 当 `failure_reason` 为空时，通常表示当前授权链路未发生 license 失败

## 16.13 半自动脚手架生成入口

当前仓库已补充半自动脚手架脚本：

- `scripts/generate_capability_scaffold.ps1`

当前脚本定位：

- 生成新增能力的基础文件骨架
- 避免手工遗漏插件 / SDK / DLL / JNI 文件名与类名
- 半自动追加 `plugins` / `linux_so` / `windows_dll` / `jni` 的 `CMakeLists.txt` 目标定义
- 明确打印后续仍需手工完成的接线步骤

当前脚本**仍不会**自动修改以下文件：

- `config/plugins_registry.txt`
- 运行时测试与测试入口
- 验收与 README 文档

这样做的目的是降低误改风险，优先保证：

- 不覆盖已有文件
- 仅对结构稳定的 `CMakeLists.txt` 做可审查的追加型接线
- 将高风险入口继续保留为人工确认步骤
