# 03 — 系统架构设计

## 3.0 架构演进目标

平台总体架构不仅服务于 Docker 一体化部署，还需要服务于以下交付形态：

1. **平台版**：HTTP 服务 + Runtime + 多能力插件。
2. **SDK 版**：单能力 Linux SO/DLL/JNI 交付。
3. **多平台版**：Linux x86_64、Windows x86_64、Linux ARM64。

因此系统架构必须坚持“**统一推理内核 + 多外壳交付**”原则：

- Runtime、插件接口、模型包规范统一。
- HTTP 服务只是其中一种外层适配器。
- JNI、Windows DLL、纯 C/C++ SDK 共享同一套能力插件内核。

## 3.2 组件职责矩阵

| 组件 | 职责 | 不负责 |
|------|------|--------|
| **HTTP 服务层** | 接收请求、参数校验、JSON 序列化、日志、路由、授权状态暴露 | 不做模型推理、不管理插件生命周期 |
| **Runtime 层** | 插件加载/卸载、实例池管理、并发调度、reload/rollback、模型缓存 | 不处理 HTTP 协议、不做业务逻辑 |
| **插件层** | 模型加载、预处理、推理、后处理、结果序列化 | 不管理网络、不管理并发、不管理授权 |
| **模型包层** | 提供模型文件、配置、阈值、manifest | 被动层，不含运行逻辑 |

## 3.3 核心数据流

### 3.3.1 推理请求数据流

```
1. Client POST /api/v1/infer/face_detect
   Body: { "image": "base64..." , "params": {...} }
   
2. HTTP 层:
   a. 解析 JSON
   b. 校验必填参数
   c. 检查 License (能力级别)
   d. 构建 InferRequest { capability_id, image_data, params }
   e. 调用 Runtime.infer(request)
   
3. Runtime 层:
   a. 查找 capability_id 对应的 PluginEntry
   b. 从实例池获取可用 CapabilityInstance
   c. 准备 PluginInput 结构体 (C ABI)
   d. 调用 plugin->infer(handle, &input, &output)
   e. 将 PluginOutput 转为 InferResult
   f. 归还 CapabilityInstance 到池中
   g. 返回 InferResult

4. 插件层 (SO 内部):
   a. 解码图像 (OpenCV)
   b. 预处理 (resize, normalize, transpose)
   c. ONNX Runtime 推理
   d. 后处理 (NMS, 阈值过滤等)
   e. 填充 PluginOutput 结构体
   f. 返回状态码
   
5. HTTP 层:
   a. 将 InferResult 序列化为 JSON
   b. 统一响应格式返回
   { "code": 0, "message": "success", "data": {...}, "request_id": "xxx", "cost_ms": 42 }
```

### 3.3.2 启动初始化数据流

```
1. 容器启动 → 主进程 main()

2. 加载平台配置
   a. 读取 /app/config/platform.yaml (镜像内置)
   b. 检查 /opt/ai_platform/config/platform.yaml (宿主机覆盖)
   c. 合并配置 (宿主机优先)

3. License 校验
   a. 读取 license 文件
   b. 验证数字签名
   c. 校验机器指纹
   d. 校验有效期
   e. 解析授权能力范围
   f. 失败则进入"受限模式" (仅暴露 health + license 状态接口)

4. Runtime 初始化
   a. 扫描插件目录 (宿主机优先，回退镜像内置)
   b. 对每个 SO: dlopen → 获取接口函数指针
   c. 对每个插件: 加载对应模型包 manifest → 校验 checksum
   d. 调用 plugin->init() → 创建 N 个实例填充实例池
   e. 注册到能力路由表

5. HTTP 服务启动
   a. 注册路由
   b. 绑定端口 (默认 8080)
   c. 开始监听

6. 日志输出：已加载能力列表、版本、实例数
```

### 3.3.3 Reload 数据流

```
1. POST /api/v1/admin/reload
   Body: { "target": "face_detect", "type": "model" | "plugin" | "all" }

2. Runtime Reload 控制器:
   a. 标记目标能力为 "reloading" 状态
   b. 等待该能力所有正在进行的推理完成 (drain)
   c. 根据 type:
      - model: 重新加载模型包，校验 manifest
      - plugin: dlclose 旧 SO → dlopen 新 SO → 重新初始化
      - all: 先 plugin 再 model
   d. 创建新实例池
   e. 原子切换：用新实例池替换旧实例池
   f. 销毁旧实例
   g. 标记能力为 "ready"
   
3. 异常回滚:
   a. 如果新版本初始化失败
   b. 保留旧实例池不销毁
   c. 标记能力恢复为 "ready"
   d. 记录错误日志
   e. 返回 reload 失败
```

## 3.4 核心类/结构体设计

### 3.4.1 HTTP 层核心结构

```cpp
// 统一推理请求
struct InferRequest {
    std::string request_id;         // 请求唯一ID
    std::string capability_id;      // 能力标识
    std::vector<ImageData> images;  // 输入图像(支持多张)
    std::vector<MediaData> media;   // 扩展媒体输入(视频/帧序列等)
    nlohmann::json params;          // 额外参数
    int64_t timestamp;              // 请求时间戳
};

// 图像数据
struct ImageData {
    std::vector<uint8_t> data;      // 原始图像字节
    std::string format;             // "jpeg", "png", "bmp"
    std::string source;             // "base64", "url", "file"
};

// 扩展媒体数据
struct MediaData {
    std::string media_type;         // "image", "video", "frame_sequence"
    std::vector<uint8_t> data;      // 文件字节或媒体数据
    std::string format;             // "mp4", "avi", "jpeg", ...
    std::string source;             // "base64", "file"
    int frame_rate = 0;             // 视频帧率，可选
};

// 统一推理结果
struct InferResult {
    int code;                       // 状态码 (0=成功)
    std::string message;            // 状态消息
    nlohmann::json data;            // 推理结果
    std::string request_id;         // 请求ID
    double cost_ms;                 // 耗时(毫秒)
};

// 统一 HTTP 响应
struct ApiResponse {
    int code;
    std::string message;
    nlohmann::json data;
    std::string request_id;
    double cost_ms;
    std::string api_version;
};
```

### 3.4.2 Runtime 层核心结构

```cpp
// 插件注册信息
struct PluginEntry {
    std::string capability_id;
    std::string so_path;
    std::string model_dir;
    void* dl_handle;                // dlopen 句柄
    PluginInterface* interface;     // C ABI 函数指针集合
    std::string version;
    std::string status;             // "ready", "reloading", "error", "disabled"
};

// 插件接口函数指针集
struct PluginInterface {
    // 生命周期
    fn_plugin_init          init;
    fn_plugin_destroy       destroy;
    fn_plugin_infer         infer;
    fn_plugin_reload        reload;
    fn_plugin_get_info      get_info;
    // 可选
    fn_plugin_warmup        warmup;     // 预热
    fn_plugin_health_check  health;     // 健康检查
};

// 能力实例池
class CapabilityPool {
public:
    PluginHandle* acquire(int timeout_ms);  // 获取实例
    void release(PluginHandle* handle);     // 归还实例
    int available_count();                  // 可用实例数
    int total_count();                      // 总实例数
    void drain();                           // 等待所有实例归还
    void replace(std::vector<PluginHandle*> new_instances); // 原子替换
private:
    std::queue<PluginHandle*> pool_;
    std::mutex mutex_;
    std::condition_variable cv_;
    int max_instances_;
};

// 插件管理器
class PluginManager {
public:
    bool load_plugin(const std::string& capability_id, const std::string& so_path);
    bool unload_plugin(const std::string& capability_id);
    bool reload_plugin(const std::string& capability_id);
    PluginEntry* get_plugin(const std::string& capability_id);
    std::vector<CapabilityInfo> list_capabilities();
};
```

## 3.5 线程模型

```
主进程
├── HTTP 监听线程 (1)
├── HTTP 工作线程池 (N, 默认 CPU 核数)
│   ├── Worker-1 → Runtime.infer() → 获取实例 → 插件推理 → 归还实例
│   ├── Worker-2
│   └── Worker-N
├── 健康检查线程 (1) — 定期检查各能力状态
├── License 监控线程 (1) — 定期检查授权状态
└── Admin 管理线程 (1) — 处理 reload/rollback 请求
```

**并发约束**：
- HTTP 工作线程数可配置，默认为 CPU 逻辑核数
- 每个能力的实例池大小可独立配置，默认为 2
- GPU 能力的实例池大小受 GPU 显存限制
- Reload 操作与推理操作互斥（通过 drain 机制）

## 3.6 CUDA/CPU 自动切换机制

```cpp
// 启动时检测
enum class DeviceType { CUDA, CPU };

DeviceType detect_device() {
    // 1. 检查 CUDA 驱动是否存在
    // 2. 检查 CUDA Runtime 版本
    // 3. 检查可用 GPU 数量
    // 4. 检查 GPU 显存是否足够
    // 如果以上任一失败，回退到 CPU
}

// ONNX Runtime Session 创建
Ort::SessionOptions create_session_options(DeviceType device) {
    Ort::SessionOptions opts;
    if (device == DeviceType::CUDA) {
        OrtCUDAProviderOptions cuda_opts;
        cuda_opts.device_id = 0;
        cuda_opts.arena_extend_strategy = 0;
        cuda_opts.gpu_mem_limit = configurable_limit;
        cuda_opts.cudnn_conv_algo_search = OrtCudnnDefaultConvAlgoSearch;
        opts.AppendExecutionProvider_CUDA(cuda_opts);
    }
    // CPU 始终作为 fallback provider
    opts.SetIntraOpNumThreads(num_threads);
    opts.SetGraphOptimizationLevel(GraphOptimizationLevel::ORT_ENABLE_ALL);
    return opts;
}
```

## 3.8 错误处理策略

| 错误类型 | 处理方式 |
|---------|---------|
| **请求参数错误** | HTTP 层直接返回 400，不进入 Runtime |
| **能力不存在** | HTTP 层直接返回 404 |
| **能力被禁用** | HTTP 层直接返回 403 + 原因 |
| **License 无效** | HTTP 层返回 403 + License 状态 |
| **实例池耗尽** | Runtime 层等待超时后返回 503 |
| **插件推理失败** | Runtime 层捕获错误，归还实例，返回 500 + 错误码 |
| **插件崩溃/段错误** | 进程级隔离（未来可用子进程），当前记录日志 + 标记能力异常 |
| **模型文件损坏** | 加载时 checksum 校验失败，能力标记为 error |
