# ai_capability_platform 产品设计文档

## 1. 文档目标

定义 ai_capability_platform 的产品定位、目标用户、业务范围、核心能力、交付物与关键约束，明确“内部工业级研发平台 + 外部工业级交付底座”的组合产品目标，为后续架构设计、模块设计和实施计划提供统一基线。

## 2. 产品定位

ai_capability_platform 是一套面向工业级 AI 能力生产与商业交付的平台体系，覆盖从样本标注、模型训练、模型测试、授权管理、推理库构建、生产镜像构建，到交付验收材料输出的完整内部研发流程，并以真实工业运行底座为最终交付载体。

平台服务于两个明确分层的场景：

1. **内部研发测试场景**：使用交互式 Web/UI 管理各类数据、任务、模型、授权、构建与验收流程，形成完整内部生产线。
2. **客户交付场景**：输出生产镜像、Linux SDK、JNI SDK、Windows SDK、授权文件、授权工具、挂载模板与交付文档，支撑客户在服务器、现有后台系统或桌面端软件中集成 AI 能力。

## 3. 产品愿景

1. 建设“工业级上层平台 + 工业级运行底座”的组合产品。
2. 统一 AI 能力从数据到交付的全生命周期管理。
3. 让内部团队通过专业管理界面完成研发测试流程闭环。
4. 让对外交付产物基于真实高并发、高可靠、可更新的 C++ 运行底座。
5. 通过授权、版本、回滚和验收体系支撑商业化交付。

## 4. 目标用户

### 4.1 内部用户

1. 数据标注工程师
2. 算法工程师
3. 测试工程师
4. 交付工程师
5. 运维工程师
6. 产品与项目管理人员

### 4.2 外部用户

1. 直接以 Docker API 方式接入 AI 能力的企业客户技术团队
2. 需要在 Java 后台系统中集成 JNI SDK 的合作方
3. 需要在 Windows 服务或桌面软件中集成 DLL SDK 的合作方
4. 需要离线授权和现场更新能力的交付现场团队

## 5. 产品边界

### 5.1 平台纳入范围

1. 数据集目录接入与样本标记管理
2. AI 能力训练任务管理与模型产出管理
3. AI 模型单接口测试、批量测试、生产镜像验收测试、测试报告管理
4. 客户、公私钥、授权文件、授权策略、授权工具管理
5. AI 能力推理库构建与多平台产物组织
6. 生产镜像构建、运行底座打包与交付材料生成
7. 运行时能力发现、模型装载、授权校验、热更新与回滚
8. 交付包目录、挂载模板、部署手册、验收手册输出

### 5.2 平台暂不纳入范围

1. 分布式训练集群调度系统
2. 公有云托管式多租户 SaaS 计费系统
3. 自动化数据采集系统
4. 客户现场在线授权签发服务

## 6. 核心业务流程

### 6.1 内部研发测试流程

1. 创建或注册 AI 能力
2. 绑定宿主机数据集目录
3. 进行样本标注与数据版本管理
4. 发起训练任务并产出模型
5. 使用 ai-test 进行单测、批测与验收测试
6. 生成测试报告与验收结论
7. 在 ai-license-mgr 中生成客户授权材料
8. 在 ai-builder 中构建推理库、SDK、生产镜像与交付包
9. 对生产镜像进行人工测试、验收测试与交付前确认

### 6.2 客户交付流程

1. 输出生产镜像压缩包
2. 输出 Linux / JNI / Windows SDK 包
3. 输出授权文件与授权查询工具
4. 输出挂载目录模板与部署/更新/验收手册
5. 客户现场部署后通过 API、JNI 或 DLL 集成能力
6. 后续通过 license、模型、插件与镜像版本执行增量更新

### 6.3 Web 产品主流程入口

1. `ai-train`：承担“标注 / 训练 / 模型管理”三类核心研发页面，强调样本工作台、训练工作台与模型资产台的连续切换。
2. `ai-test`：承担“单测 / 批测 / 验收 / 报告”页面，并作为生产测试主入口，负责承接训练产物后的评估闭环。
3. `ai-license-mgr`：承担“客户 / 密钥 / 策略 / 签发 / 校验 / tool release”页面，负责商业授权闭环。
4. `ai-builder`：承担“构建配置 / 实时日志 / 产物 / delivery_package / 镜像构建上下文”页面，负责交付构建闭环。
5. `ai-prod`：定位为“内部运行控制台”，承担在线演示、运行监控、reload / rollback、版本与诊断查询，不作为客户业务前台。
6. 后续统一门户需要以“标注 → 训练 → 测试 → 授权 → 构建 → 生产验收”六步流程组织导航，而不是按技术模块名堆叠入口。

## 7. 产品子系统定义

### 7.1 ai-train

职责：面向内部研发流程提供样本标注、训练管理、模型管理、能力元数据管理与训练模板管理能力。

### 7.2 ai-test

职责：面向内部研发与交付验收提供模型测试、批量测试、生产镜像验收测试、测试报告生成与归档能力。

### 7.3 ai-license-mgr

职责：提供客户管理、密钥对管理、授权策略管理、授权文件签发、授权工具管理与授权审计能力。

### 7.4 ai-builder

职责：提供能力推理库编译、生产镜像打包、多平台 SDK 打包、交付包目录组织、文档材料归档与验收物料输出能力。

### 7.5 ai-prod

职责：作为对外交付的真实工业运行底座，采用 C++ HTTP 服务 + C++ Runtime + 插件模式提供高并发推理、热更新、回滚与授权校验能力；同时提供供内部测试/验收使用的 Web/UI 交互外壳。

### 7.6 单机交付 SDK

职责：面向第三方交付 Linux SO、JNI SO、Windows DLL、头文件、模型包、授权材料、示例工程与接入说明。

## 8. 核心产品能力

### 8.1 AI 能力生产线能力

1. 新增能力时同步补齐训练、测试、推理、构建模板。
2. 能力元数据统一注册，供 train/test/builder/prod 查询。
3. 内部各管理系统提供专业化 Web/UI 交互体验。

### 8.2 数据与模型资产管理

1. 宿主机固定目录接入
2. 数据集与能力绑定
3. 模型版本化管理
4. 测试报告、构建产物、交付包可追溯

### 8.3 交付与更新能力

1. Docker 交付、Linux SDK、JNI SDK、Windows SDK 并行支持
2. 交付包输出统一目录结构与验收材料
3. 支持 license、模型、插件、镜像版本管理
4. 支持 reload 与回滚
5. 支持授权查询工具与挂载模板输出

### 8.4 工业级运行能力

1. 生产主链路采用 C++ HTTP + C++ Runtime + 插件模式
2. GPU 优先、CPU 自动回退
3. 统一错误码、日志与审计
4. 运行状态、能力列表、授权状态、版本状态可观测
5. 支持高并发与插件级故障隔离

### 8.5 全流程 Web 产品化体验

1. 所有内部模块必须采用统一工作台壳层：顶部产品导航、左侧模块内导航、主内容区、右侧详情 / 日志 / 帮助抽屉。
2. 页面设计优先围绕“对象 + 流程 + 状态”展开，而不是单纯罗列接口返回值；对象包括数据集、标注任务、训练任务、模型、测试任务、license、构建任务、运行版本等。
3. 每个模块首页都应提供：
   - 当前阶段待办
   - 核心对象统计
   - 最近任务 / 异常
   - 跨模块下一步动作入口
4. 全流程必须建立对象跳转关系：
   - 训练任务 / 模型可直接进入测试
   - 测试通过结果可直接进入授权 / 构建
   - 构建完成产物可直接进入生产验收
   - 所有页面应尽量避免人工复制 ID
5. 统一交互要求：
   - 长流程页面采用“列表 + 详情工作台”双栏结构
   - 创建流程优先采用分步向导
   - 实时任务优先采用日志面板、阶段状态条、结果摘要卡片
   - 高风险操作需要显式确认与审计提示
6. 统一视觉要求：
   - 研发工作台采用高信息密度但强分组布局
   - 主色、状态色、图表风格、卡片规格、按钮优先级保持一致
   - 支持大屏联调与常见笔记本分辨率，重点流程避免首屏滚动后才见关键操作
7. 统一企业级能力要求：
   - 角色权限、审计日志、异常告警、批量操作、断点恢复、导出下载
   - 对大文件、长任务、批量对象提供队列状态、进度反馈与失败重试入口
8. 产品化改造时，应优先把现有“能做但难用”的页面收口为专业工作台，而不是额外增加新的演示页。

## 9. 非功能需求

### 9.1 性能

1. 生产接口支持高并发调用。
2. Runtime 采用能力实例池，不允许单全局锁串行化推理。
3. Python Web/UI 仅作为内部测试与验收交互外壳，不能替代生产主调用链路。

### 9.2 稳定性

1. 核心更新操作支持原子切换。
2. 支持健康检查、版本检查和回滚。
3. 插件故障隔离，避免单能力异常拖垮全系统。

### 9.3 安全

1. 授权采用数字签名机制。
2. 生产服务启动时与推理时必须双层校验授权。
3. 文件导入、构建、测试接口需限制输入类型、大小与路径访问。
4. 私钥签发侧与客户运行侧必须逻辑隔离。

### 9.4 可维护性

1. 文档先行
2. 模块边界清晰
3. 统一规范
4. 支持增量开发与迭代跟踪
5. 实际实现必须持续回对设计文档与开发计划

## 10. 交付物定义

### 10.1 标准交付包

```text
delivery_package/
├── docker/
│   ├── agilestar-ai-prod-linux-x86_64-v<version>.tar.gz
│   └── agilestar-ai-prod-linux-aarch64-v<version>.tar.gz
├── sdk_linux_x86_64/
├── sdk_linux_aarch64/
├── sdk_windows_x86_64/
├── sdk_windows_x86/
├── licenses/
│   └── license.bin
├── mount_template/
├── docs/
│   ├── API文档.md
│   ├── 部署手册.md
│   ├── 更新手册.md
│   └── 验收手册.md
└── tools/
    └── license_tool
```

### 10.2 面向不同客户的核心产物

1. **生产镜像**：面向通过 Docker 部署并以 API 调用 AI 能力的客户。
2. **JNI SDK .so**：面向在现有 Java 后台服务中集成 AI 能力的客户。
3. **Windows SDK .dll**：面向在 Windows 后台系统或桌面软件中集成 AI 能力的客户。
4. **授权文件**：所有商业交付的必需文件。
5. **授权工具**：用于采集或查询硬件信息的必需工具。
6. **API 文档与部署/更新/验收手册**：客户部署与验收参考材料。

## 11. 关键约束

1. CUDA 固定为 11.8。
2. 所有文件统一 UTF-8。
3. 注释与 git 提交说明统一中文。
4. 宿主机映射端口从 26000 起连续规划。
5. C++ 采用 Google 风格，但禁用成员变量尾下划线命名。
6. npm 下载优先使用国内源。
7. 对外交付运行底座必须优先复用统一 C++ Runtime 内核。

## 13. 成功判定标准

1. 各子系统职责明确，边界清晰。
2. 文档体系覆盖产品、架构、模块、规范、评审、计划。
3. 内部研发测试流程可通过 Web/UI 完成完整闭环。
4. 新增 AI 能力可以沿统一模板完成训练、测试、构建与交付。
5. 对外交付支持真实工业运行底座、现场更新、回滚、授权控制与多能力并发推理。
6. 标准交付包能够输出镜像、SDK、license、工具、文档与挂载模板。
7. 五个内部 Web 模块具备统一导航、统一工作台布局、统一对象跳转与统一状态表达。
8. `ai-test`、`ai-builder`、`ai-license-mgr`、`ai-prod` 页面体验与专业深度能与当前 `ai-train` 的真实交互水平对齐，不再停留在展示页 / 看板页。
