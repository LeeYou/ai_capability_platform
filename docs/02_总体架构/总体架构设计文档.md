# ai_capability_platform 总体架构设计文档

## 1. 架构目标

1. 建立面向 AI 能力全生命周期的统一上层平台架构。
2. 建立面向客户交付的统一运行底座与交付规范。
3. 在保留当前平台训练/测试/授权/构建优势的前提下，吸收 `ai_platform` 在 Runtime、交付目录、License、热更新与回滚方面的成熟设计。
4. 满足工业级对扩展性、稳定性、可运维性、安全性和交付性的要求。

## 2. 总体架构原则

1. 文档先行，设计驱动实现。
2. 一个 AI 能力对应一套能力元数据、一组训练/测试模板和一套插件模板。
3. 内部研发链路与客户交付链路分层建设，但通过统一元数据、ABI、manifest、license schema 打通。
4. 上层平台优先采用 Python + React 提供专业管理体验。
5. 运行底座优先采用 C++ HTTP 服务 + C++ Runtime + 插件模式，保障高并发与真实工业运行能力。
6. 镜像内置基线 + 宿主机挂载覆盖优先。
7. GPU 优先，CPU 自动回退。
8. 版本化、原子切换、可回滚。
9. 默认 Docker 交付，同时支持 Linux SO、JNI SO、Windows DLL 交付。

## 3. 逻辑架构

### 3.1 双层产品架构

1. **上层平台（内部使用）**：ai-train、ai-test、ai-license-mgr、ai-builder、ai-sdk 等管理与研发测试系统。
2. **运行底座（客户交付）**：ai-prod C++ HTTP 服务、C++ Runtime、Capability 插件、模型包、License、挂载模板与工具链。

### 3.2 平台层次

1. 门户与管理层：各子系统 Web 管理界面与 API。
2. 业务服务层：训练、测试、授权、构建、交付管理服务。
3. 共享基础层：能力注册中心、模型元数据、manifest/license schema、任务编排、审计日志、文件存储规则。
4. 交付编排层：交付包组装、镜像归档、SDK 打包、验收文档输出、挂载模板输出。
5. 交付运行层：C++ HTTP 服务层、C++ Runtime 层、Capability 插件层、模型包层、License 校验层。
6. 基础设施层：Docker、CUDA 11.8、SQLite/后续可扩展数据库、宿主机挂载目录、GPU/CPU 环境。

### 3.3 子系统关系

1. ai-train 维护能力、数据集、训练任务与模型主数据。
2. ai-test 从 ai-train 查询模型与能力信息，并对模型、推理库和生产镜像执行验收测试。
3. ai-license-mgr 维护客户、公钥、license、授权策略与授权工具。
4. ai-builder 从 ai-train 获取能力与模型，从 ai-license-mgr 获取授权信息，构建插件、SDK、生产镜像与最终交付包。
5. ai-prod 消费 ai-builder 输出的运行产物，以 C++ 服务提供生产推理能力。
6. ai-sdk 负责将标准 ABI 和示例工程组织为第三方可集成的单机交付形态。

## 4. 部署架构

### 4.1 内部研发环境容器

1. ai-train 容器
2. ai-test 容器
3. ai-license-mgr 容器
4. ai-builder 容器
5. ai-sdk 容器
6. 内部验收用 ai-prod 测试容器或测试镜像

各容器均使用宿主机挂载目录进行数据持久化与共享。

### 4.2 客户交付运行形态

1. **Docker 平台版**：C++ HTTP 服务 + C++ Runtime + 多能力插件 + 模型 + License。
2. **Linux SO SDK**：单能力或多能力 SO、头文件、模型包、license、说明文档。
3. **JNI SDK**：JNI 桥接库 + SO + 模型包 + 说明文档。
4. **Windows DLL SDK**：DLL + import lib/头文件 + 模型包 + 说明文档。

### 4.3 内部测试外壳

为提升人工测试和验收体验，可提供 Python FastAPI + React 的测试页面外壳。该外壳仅服务于内部测试、演示与验收，内部通过 HTTP 或桥接方式转调 C++ 生产服务，不作为客户生产主链路。

## 5. 宿主机与交付目录架构

### 5.1 内部研发根目录

推荐根目录：`/data/ai_capability_platform/`

1. `data/`：SQLite、业务数据、测试报告、审计日志
2. `datasets/`：按能力划分的数据集目录
3. `models/`：模型包版本目录
4. `license/`：`license.bin`、`pubkey.pem`、签发记录
5. `libs/`：多平台推理库产物目录
6. `configs/`：系统配置、阈值、路由映射
7. `logs/`：运行日志
8. `exports/`：交付包、测试报告、构建清单、验收材料

### 5.2 客户交付运行根目录

推荐根目录：`/opt/ai_platform/`

1. `plugins/`：SO/DLL/JNI 运行库
2. `models/`：模型包目录
3. `license/`：授权文件
4. `config/`：`platform.yaml`、`plugins_registry.txt` 等配置
5. `logs/`：运行日志与审计日志

### 5.3 标准交付包目录

由 ai-builder 统一输出 `delivery_package/`，包含 docker、各平台 SDK、licenses、mount_template、docs、tools 六类内容。

## 6. 生产运行架构

### 6.1 Layer 1：C++ HTTP 服务层

职责：

1. REST API
2. 参数校验
3. 能力路由
4. 授权状态暴露
5. 健康检查
6. 管理接口
7. 统一 JSON 返回
8. 高并发网络处理

### 6.2 Layer 2：C++ Runtime 层

职责：

1. 动态加载/卸载能力插件
2. 模型包校验与装载
3. 能力实例池管理
4. GPU/CPU 后端选择
5. 统一错误码
6. reload/rollback
7. 版本切换与实例 drain

### 6.3 Layer 3：Capability 插件层

职责：

1. 每个能力一个 SO/DLL
2. 对外暴露标准 C ABI
3. 实现初始化、推理、重载、查询、销毁
4. 与 Linux SO / JNI / Windows DLL 交付形态共享核心能力实现

### 6.4 Layer 4：模型包层

职责：

1. 存放部署模型文件
2. 存放 manifest、预处理配置、阈值、标签、checksum
3. 支撑模型版本与交付版本映射

### 6.5 Layer 5：测试与验收外壳层（内部可选）

职责：

1. 提供人工测试页面和演示页面
2. 调用或转发到 C++ HTTP 服务
3. 不承担客户生产主调用压力

## 9. 并发与线程安全架构

1. 不允许依赖可变全局静态状态。
2. 每个能力采用实例池而非单例大锁。
3. 实例独享上下文、工作缓冲区与必要计算资源。
4. reload 与推理隔离，采用读写版本切换机制。
5. 返回数据使用显式内存所有权协议。
6. Python 管理系统不得承载生产高并发主链路。

## 10. 版本、更新与回滚架构

### 10.1 版本化组织

1. 模型版本目录
2. 插件版本目录
3. license 版本目录
4. 镜像版本目录
5. `current` 或活动指针

### 10.2 更新流程

1. 新版本落盘到新目录
2. 校验 manifest/checksum/license 兼容性
3. 原子切换 current
4. 执行 reload
5. 失败自动回滚
6. 记录版本切换审计日志

## 11. 安全架构

1. 训练、测试、构建、导入接口需做输入校验和路径白名单控制。
2. 生产服务启动时和推理时双层校验 license。
3. 客户授权采用私钥签名、公钥验签。
4. 机器绑定采用多硬件特征组合哈希。
5. 所有关键操作记录审计日志。
6. 私钥签发侧与客户运行侧隔离部署。

## 12. 技术架构决策

1. 管理系统后端优先 Python FastAPI。
2. 管理系统前端优先 React + TypeScript。
3. 训练/测试脚本优先 Python + PyTorch/ONNX Runtime。
4. 推理库、Runtime、生产 HTTP 服务优先 C++ + ONNX Runtime + CMake。
5. 内部测试页面采用 Python FastAPI 或 React 外壳，但必须转调 C++ 生产服务。
6. 交付工具和 license_tool 采用 C++ 或最小依赖 CLI 方案，便于现场运行。

## 13. 可观测性架构

1. 健康检查
2. 授权状态查询
3. 插件加载状态查询
4. 模型版本查询
5. delivery package 版本清单
6. 结构化日志
7. 审计日志

## 14. 架构落地要求

1. 先完成统一文档体系与开发计划刷新，再进入融合实现。
2. 先固化标准 C ABI、manifest、license schema、交付目录规范，再推进 builder/prod/SDK 收敛。
3. ai-prod 下一阶段实现必须以 `ai_platform` 的 Runtime、HTTP、License、更新回滚设计为参考基线。
4. ai-builder 下一阶段实现必须输出标准 `delivery_package/` 与验收材料。
5. 所有模块开发必须持续对照本架构文档、模块设计文档与开发计划执行。
