# ai_capability_platform 总体架构设计文档

## 1. 架构目标

1. 建立面向 AI 能力全生命周期的统一架构。
2. 支撑多子系统独立演进，同时共享统一能力元数据、模型元数据、授权规则和交付规范。
3. 满足工业级对扩展性、稳定性、可运维性、安全性和交付性的要求。

## 2. 总体架构原则

1. 文档先行，设计驱动实现。
2. 一个 AI 能力对应一套能力元数据与一组插件模板。
3. 研发链路与交付链路解耦，但通过统一元数据打通。
4. 镜像内置基线 + 宿主机挂载覆盖优先。
5. GPU 优先，CPU 自动回退。
6. 版本化、原子切换、可回滚。
7. 默认 Docker 交付，兼容 SDK/JNI 单机交付。

## 3. 逻辑架构

### 3.1 平台层次

1. 门户与管理层：各子系统 Web 管理界面与 API。
2. 业务服务层：训练、测试、授权、构建、交付管理服务。
3. 共享基础层：能力注册中心、模型元数据、任务编排、审计日志、文件存储规则。
4. 交付运行层：HTTP 服务层、Runtime 层、Capability 插件层、模型包层。
5. 基础设施层：Docker、CUDA 11.8、SQLite/后续可扩展数据库、宿主机挂载目录、GPU/CPU 环境。

### 3.2 子系统关系

1. ai-train 维护能力与模型主数据。
2. ai-test 从 ai-train 查询模型与能力信息并生成测试结果。
3. ai-license-mgr 维护客户、公钥、license 与授权策略。
4. ai-builder 从 ai-train 获取能力与模型，从 ai-license-mgr 获取授权信息，生成推理库交付物。
5. ai-prod 读取 ai-builder 产物、模型包与授权文件，提供生产推理服务。

## 4. 部署架构

### 4.1 研发环境容器

1. ai-train 容器
2. ai-test 容器
3. ai-license-mgr 容器
4. ai-builder 容器

各容器均使用宿主机挂载目录进行数据持久化与共享。

### 4.2 生产环境容器

1. 统一 ai-prod 生产镜像
2. 可选挂载模型、SO、license、配置、日志目录
3. 对外暴露 REST API 与测试页面

## 5. 宿主机目录架构

推荐根目录：`/data/ai_capability_platform/`

1. `data/`：SQLite、业务数据、测试报告、审计日志
2. `datasets/`：按能力划分的数据集目录
3. `models/`：模型包版本目录
4. `license/`：`license.bin`、`pubkey.pem`
5. `libs/`：多平台推理库产物目录
6. `configs/`：系统配置、阈值、路由映射
7. `logs/`：运行日志
8. `exports/`：导出测试报告、构建清单、验收材料

## 6. 生产容器四层架构

### 6.1 HTTP 服务层

职责：

1. REST API
2. 参数校验
3. 能力路由
4. 授权状态暴露
5. 健康检查
6. 管理接口
7. 统一 JSON 返回

### 6.2 Runtime 层

职责：

1. 动态加载/卸载能力插件
2. 模型包校验与装载
3. 能力实例池管理
4. GPU/CPU 后端选择
5. 统一错误码
6. reload/rollback

### 6.3 Capability 插件层

职责：

1. 每个能力一个 SO/DLL
2. 对外暴露标准 C ABI
3. 实现初始化、推理、重载、查询、销毁

### 6.4 模型包层

职责：

1. 存放部署模型文件
2. 存放 manifest
3. 存放预处理、阈值、标签、校验信息

5. `/api/v1/admin/reload`

## 9. 并发与线程安全架构

1. 不允许依赖可变全局静态状态。
2. 每个能力采用实例池而非单例大锁。
3. 实例独享上下文、工作缓冲区与必要计算资源。
4. reload 与推理隔离，采用读写版本切换机制。
5. 返回数据使用显式内存所有权协议。

## 10. 版本与更新架构

### 10.1 版本化组织

1. 模型版本目录
2. 插件版本目录
3. license 版本目录
4. `current` 或活动指针

### 10.2 更新流程

1. 新版本落盘到新目录
2. 校验 manifest/checksum/license 兼容性
3. 原子切换 current
4. 执行 reload
5. 失败自动回滚

## 11. 安全架构

1. 训练、测试、构建、导入接口需做输入校验和路径白名单控制。
2. 生产服务启动时和推理时双层校验 license。
3. 客户授权采用私钥签名、公钥验签。
4. 机器绑定采用多硬件特征组合哈希。
5. 所有关键操作记录审计日志。

## 12. 技术架构决策

1. 管理系统后端优先 Python FastAPI。
2. 管理系统前端优先 React + TypeScript。
3. 训练/测试脚本优先 Python + PyTorch/ONNX Runtime。
4. 推理库优先 C++ + ONNX Runtime + CMake。
5. 生产服务首选 C++ HTTP 服务或 Python 网关 + C++ Runtime 的混合方案。首期建议采用 Python FastAPI + C++ Runtime 动态库桥接，降低管理面与运行面集成复杂度。

## 13. 可观测性架构

1. 健康检查
2. 授权状态查询
3. 插件加载状态查询
4. 模型版本查询
5. 结构化日志
6. 审计日志

## 14. 架构落地要求

1. 先完成统一文档体系与模板工程。
2. 先建设能力注册与元数据协议，再推进各子系统实现。
3. 先定义标准 C ABI、manifest、license schema，再推进 builder/prod。
4. 所有模块开发必须对照本架构文档执行。
