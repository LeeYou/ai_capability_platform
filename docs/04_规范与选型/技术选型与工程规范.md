# 技术选型与工程规范

## 1. 技术选型总原则

1. 优先选择主流、成熟、安全、长期维护的技术栈。
2. 管理面与运行面技术解耦。
3. 训练、测试、构建、交付共享统一元数据、ABI 与协议规范。
4. 严格围绕 CUDA 11.8 做兼容性控制。
5. 内部平台优先保障研发效率与管理体验，外部交付优先保障运行性能与稳定性。

## 2. 技术选型

### 2.1 管理系统

1. 前端：React + TypeScript + Vite
2. 后端：Python 3.11 + FastAPI
3. ORM：SQLModel 或 SQLAlchemy
4. 数据库：SQLite（首期），预留后续升级 PostgreSQL

### 2.2 AI 与交付相关

1. 训练框架：PyTorch
2. 内部测试推理：Python + ONNX Runtime
3. 生产推理：C++ + ONNX Runtime
4. Runtime：C++17
5. 生产 HTTP：C++ HTTP 服务（参考 `ai_platform` 的实现路线）
6. 构建系统：CMake

### 2.3 生产服务与测试外壳

1. 客户生产主链路：C++ HTTP + C++ Runtime + 插件模式
2. 内部测试/验收外壳：FastAPI + React，可转调 C++ HTTP 服务
3. 容器化：Docker
4. 多架构镜像：amd64 / arm64

### 2.4 SDK 与工具

1. Linux SDK：SO + C/C++ 头文件
2. JNI SDK：JNI SO + Java 示例
3. Windows SDK：DLL + import lib + 头文件
4. license_tool：C++ CLI 或轻量无运行时依赖的本地工具

## 3. CUDA 与依赖规范

1. 全平台统一使用 CUDA 11.8。
2. 所有 GPU 相关依赖版本必须明确标注与 CUDA 11.8 兼容。
3. 不允许引入其他 CUDA 主版本依赖。
4. GPU 不可用时必须自动切换 CPU。

## 4. Docker 规范

1. Dockerfile 必须区分稳定层与频繁变更层。
2. 安装依赖优先使用缓存友好的层次结构。
3. npm 源优先配置国内源，如清华源。
4. 内部研发容器端口从 26000 起规划：
   - ai-train：26000
   - ai-test：26001
   - ai-license-mgr：26002
   - ai-builder：26003
   - ai-prod 管理/测试外壳：26004
5. 客户交付镜像中的生产主服务端口以交付配置为准，不受内部研发端口约束。
6. 生产镜像需支持镜像内置资源与宿主机挂载覆盖双层目录。

## 5. 宿主机与交付目录规范

### 5.1 内部研发根目录

根目录：`/data/ai_capability_platform/`

1. `data/`：持久化数据库、元数据、测试报告
2. `datasets/`：训练与测试数据集
3. `models/`：部署模型包
4. `license/`：授权文件与签发记录
5. `libs/`：交付推理库
6. `configs/`：运行配置
7. `logs/`：日志
8. `exports/`：导出文件与交付包

### 5.2 客户运行根目录

根目录：`/opt/ai_platform/`

1. `plugins/`
2. `models/`
3. `license/`
4. `config/`
5. `logs/`

### 5.3 标准交付包目录

ai-builder 必须输出 `delivery_package/`，包含：

1. `docker/`
2. `sdk_linux_x86_64/`
3. `sdk_linux_aarch64/`
4. `sdk_windows_x86_64/`
5. `sdk_windows_x86/`
6. `licenses/`
7. `mount_template/`
8. `docs/`
9. `tools/`

## 6. C++ 编码规范

1. 采用 Google 编码风格。
2. 严禁使用成员变量尾下划线命名方式。
3. 统一使用清晰的语义化命名。
4. 严格区分接口头文件与实现文件。
5. 显式声明线程安全边界和内存所有权。
6. Runtime、插件、HTTP 服务、license_tool、SDK 核心库均按工业级 C++ 标准实现。

## 7. Python 编码规范

1. 统一使用 Python 3.11。
2. 强制类型标注。
3. API、任务、模型逻辑分层。
4. 路径访问使用白名单目录与安全拼接。
5. Python 服务优先承担管理编排、测试外壳和内部工具职责，不承担客户生产高并发主链路。

## 8. 前端规范

1. TypeScript 严格模式。
2. 页面按子系统分域组织。
3. API 类型定义集中管理。
4. 管理页面统一展示公司信息与版本信息。
5. 标注、训练、测试、授权、构建页面需体现工业级管理体验，支持任务状态、产物状态、风险提示与审计信息展示。

## 9. API 设计规范

1. REST 风格统一。
2. 统一版本前缀 `/api/v1/`。
3. 统一错误码、错误消息、`request_id`。
4. 输入支持文件类统一抽象，涵盖图片、视频、PDF 等。
5. 内部管理 API 与客户生产 API 必须分层设计，避免把内部测试接口混入客户主链路。

## 10. 模型包规范

每个模型包至少包含：

1. 模型文件
2. manifest
3. 预处理配置
4. 阈值配置
5. 标签定义
6. checksum
7. 版本与后端声明

## 11. License 规范

license 内容至少包含：

1. `customer_id`
2. `capability_scope`
3. `hardware_fingerprint`
4. `start_at_cst`
5. `expire_at_cst`
6. `version_constraints`
7. `signature`
8. `license_type`

同时必须配套：

1. `pubkey.pem`
2. `license_tool`
3. 授权说明文档

## 12. 交付文档规范

标准交付文档至少包含：

1. `API文档.md`
2. `部署手册.md`
3. `更新手册.md`
4. `验收手册.md`
5. SDK 接入说明
6. 错误码说明

## 13. 文档规范

1. 所有文件统一 UTF-8。
2. 文档、注释、提交说明统一中文。
3. 设计文档先于实现。
4. 变更后需同步更新计划与评审文档。
5. 每轮实现前后必须回对设计文档、开发计划与实际代码状态。

## 14. 安全规范

1. 禁止硬编码密钥。
2. 禁止任意路径读写。
3. 禁止任意命令拼接执行。
4. 上传文件需校验类型、大小、存储位置。
5. 构建与生产接口必须记录审计日志。
6. 私钥签发系统与客户运行侧必须逻辑隔离。
7. 生产镜像与 SDK 必须具备 license 双层校验能力。
